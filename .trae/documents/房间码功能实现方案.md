# 房间码 / 房间列表 功能实现方案

## 背景（Context）

## 设计要点（含一个关键修正）

### ⚠️ 关键设计点：**空房间也必须登记**（这里推翻了方案初稿的一个想当然）

初稿写的是"第一个玩家进房才开始上报，避免 0 人僵尸房"。**但这和同一方案里的"创建房间 = 领一个空房"直接矛盾**——云机上的房间是**预先开好的进程池**（一进程一房间），空房间本身就是"可以创建的房间"。不让空房登记，玩家点"组队"时就查不到任何可用的房间，功能直接死掉。

所以最终设计是：

- **服务器进程启动 → 立即注册**（拿到房间码），之后每 3 秒心跳（含当前人数 / 是否对局中）
- **空房间保留在列表里**，由列表字段区分用途：`players == 0` = 可创建 ｜ `0 < players < max` = 可加入 ｜ `inGame` = 对局中不可进
- **不再"人走光就注销"**——房间空了就退回"可创建"状态即可
- **进程正常停止**时注销（让朋友立刻看不到已关闭的房间）；**进程崩溃/断网**的情况由后端 TTL（30 秒没心跳）兜底清理

### 其余要点

| # | 要点 | 做法 |
|---|---|---|
| 1 | 房间码传给客户端 | 服务器在 `GameNetworkManager` 存权威字段；拿到码后 **fan-out 写入所有 `roomSlots` 的 `RoomPlayer.roomCode`（SyncVar）**；UI 读自己的，**码为空时显示"生成中…"，绝不阻塞进房** |
| 2 | 公网 IP 从哪来 | **优先让登记服务用 HTTP 请求来源 IP 回填**（云机上这就是朋友该拨的公网 IP）；`-publicip <ip>` 作为兜底覆盖（多网卡/多公网 IP 时用） |
| 3 | 房间码唯一性 | 首次上报不带码 → 服务端生成后返回；进程记住该码。**若服务重启导致码丢失 → 服务端沿用请求里带的码重新登记**（码保持不变，体验无感） |
| 4 | 心跳健壮性 | 上报失败下个周期自动重试；后端重启后自动重新登记 |
| 5 | 满房问题 | 上报带 `maxPlayers`；列表返回 `players/maxPlayers`，客户端过滤掉满房，避免"查表成功却进不去被硬踢" |
| 6 | 不引入 MySQL | 房间登记是**易失数据**（房间进程一关就该消失），不该入库。用内存 `ConcurrentDictionary` + TTL 清扫；留一个 `IRoomStore` 接口，日后要 Redis/DB 也不返工 |
| 7 | "创建房间"怎么实现 | = **领一个空房间**（从列表挑 `players == 0` 的连入，第一个进去的人自然成为房主）。**不做加锁**——两人同时点最多一起进同一个空房，无害甚至更好。比"后端按需 spawn 进程"省掉一整套进程编排 + loading UI + 孤儿进程治理 |

## 后端（新增）

**位置**：项目根目录 `Backend/RoomRegistry/`（**不放在 `Assets/` 下**，避免 Unity 去编译它）

**技术**：ASP.NET Core Minimal API + 内存字典 + TTL 清扫。本机已具备 SDK 9.0.318 / 10.0.401、ASP.NET Core 运行时 8/9/10，可直接 `dotnet run`。

| 接口 | 用途 |
|---|---|
| `POST /api/rooms/heartbeat` | 房间注册 + 心跳。body 带 `code`(可空)/`port`/`players`/`maxPlayers`；空 code = 首次注册 → 服务端生成 4 位码（避开 `0/O/1/I` 易混字符）返回；来源 IP 由服务端回填；`code` 存在但服务端不认识（服务重启过）→ 沿用该 code 登记 |
| `DELETE /api/rooms/{code}` | 主动注销（房间空了/进程要关） |
| `GET /api/rooms` | 房间列表：`[{code, ip, port, players, maxPlayers, ageSec}]`，用于房间列表 + 快速匹配 |
| `GET /api/rooms/{code}` | 按码查单房间，用于"输码进房"；404 = 房间不存在 |

TTL：超过 30 秒没心跳 → 视为失效并清理（兜底，防房间进程崩溃后留下僵尸房）。

## 本地端到端验证

```powershell
# 1) 起后端（默认监听 5000）
cd Backend/RoomRegistry ; dotnet run

# 2) 起两个房间进程（已打好的 exe）
Start-Process -FilePath "d:\unitydemo\Blow up your brother\Build\Blow up your brother.exe" `
  -ArgumentList "-servermode","-port","7777","-lobbyserver","http://127.0.0.1:5000" `
  -WorkingDirectory "d:\unitydemo\Blow up your brother\Build"
#  再把 -port 换 7778 起第二个

# 3) 三个客户端：编辑器 Play 1 份 + Build 的 exe 2 份
#    （编辑器 GetCommandLineArgs 不含 -servermode，天然被当客户端）
```

**验收清单**：

1. 客户端 A 点"组队" → 自动连入一个空房 → 房间面板显示 4 位房间码
2. `GET /api/rooms` 能看到这条记录，人数 1/10
3. 客户端 B 输该房间码 → 成功进同一房，两边互相看到对方
4. 客户端 C 点"快速匹配" → 进入同一个未满房（而不是另开一间）
5. 全员退出房间 → `GET /api/rooms` 里该房间**立刻消失**（主动注销生效）
6. 后端 Ctrl+C 重启 → 房间进个新人 → 房间码**保持不变**（重登记生效）
7. 房间列表面板能看到两个房间、人数正确

## 部署上云（本方案只做"能部署"，实际部署等你买云机）

- 后端 `dotnet publish -c Release` → 建议 **self-contained 发布**（云机免装 .NET 运行时）
- 房间进程的 `启动服务器.bat` 加 `-lobbyserver http://<云机IP>:5000`
- 放行端口：**5000/TCP**（登记服务）+ **7777~7781/UDP**（各房间，注意是 UDP）
- 后端与房间进程同机部署即可（量小）；分开部署时第 2 点"来源 IP 回填"结论依然成立

## 待你确认的决策点

1. **云机系统选 Windows 还是 Linux？** ⚠️ 你规划定稿写的是 Linux + systemd（需装 Linux Build Support 重打无头服），但**当前已实现的专用服是 Windows 包**。选 Windows 可直接沿用现有包、部署最省事；选 Linux 要额外打一次 Linux Server 包。**这一步的代码本身完全不受影响**，只影响部署方式，可以晚点定。
2. **范围**：建议一次做完"房间码 + 房间列表 + 快速匹配"三件（如你所说是同一个服务的三个 UI，核心逻辑只有十几行）；若想切小，可先只做前两件。
3. **登记服务地址放哪**：默认值写进 `Constants` + 设置界面可改（推荐）——你认可吗？
4. 本步骤**不引入 MySQL / 账号体系**（房间登记是易失数据），你认可吗？

## 不做什么（明确边界）

- ❌ 不做后端按需拉起房间进程（进程编排/孤儿治理）——先用预开房间池
- ❌ 不做 MySQL / 登录 / 存档上云（那是阶段 3 后续，与房间码无耦合）
- ❌ 不动现有局域网 StartHost 玩法（保留双模式）
